# Security

Cross-cutting security policy. The mechanisms themselves (Argon2id parameters, opaque session
tokens, the rate limiter, transactional email) are documented in [tech-stack.md](tech-stack.md);
this page records the policy that spans them.

## Account enumeration

**The risk.** Whether an email address has an account here tells a prober that a given person is a
coach on this platform, and narrows a credential-stuffing run from the address space to the
membership.

**The policy.** Every endpoint that takes an email from an unauthenticated caller answers known and
unknown addresses identically: same status code, same body, same rate-limit behaviour. New
authentication endpoints are built to this policy.

**The one exception: sign-up.** The sign-up entry point answers "Email already registered" openly.

- A form that cannot say "you already have an account, sign in instead" tests badly, and
  low-friction setup is a priority of the brief.
- The cost is metered rather than closed: the per-email rate limit charges a probe of a registered
  address exactly as it charges a code request.

**How each path holds it:**

- **Login:** one message for an unknown email and a wrong password; a dummy Argon2 verification, so
  response time does not answer what the body refuses to; a wrong-guess budget keyed on the
  submitted address whether or not an account lives there.
- **Player login:** the same defences over the player's username, with a third case folded into the
  same message and timing: a player whose coach has not minted a password yet answers exactly like a
  wrong password, so the login form cannot say which of a club's players have been handed accounts.
  A player username is derived from the player's name by construction, so the wrong-guess budget,
  not the identifier's secrecy, is what the defence rests on.
- **Password reset:** a uniform 202 whether or not the address holds an account, and one answer at
  each later step whether or not the address behind it does.
- **Code redemption** (sign-up verification and reset codes): every failure collapses into one
  response.

**Accepted residual channels.** In the reset flow, a request for a registered address takes
measurably longer (it stores a code and sends an email), and a send failure answers 502 only for a
registered address. Both reveal nothing the sign-up entry does not already answer openly.

## Password storage

Argon2id via `argon2-cffi`, with parameters tuned for the deployment target rather than taken as
library defaults. `time_cost=3`, `memory_cost=64 MiB`, `parallelism=1`, with a semaphore capping
concurrent hashes at two. The arithmetic: each hash allocates 64 MiB, and 40 default worker threads
each doing so would exceed the API container's 512 MiB cgroup limit and trigger an OOM kill.
`parallelism=1` because the VPS has one vCPU, so extra Argon2 lanes cannot actually run in parallel.
The parameters and reasoning are recorded in `security.py`.

Each hash is salted with a unique random value generated by `argon2-cffi` at hash time. The salt is
encoded into the PHC-format output string alongside the digest, so verification extracts it
automatically. No application code manages salts.

Passwords are NFKC-normalised before hashing or verification. A composable character (e.g. e-acute)
has more than one valid encoding depending on platform and input method; hashing raw bytes would
silently lock out a coach who enrolled from one keyboard and signs in from another. NIST SP 800-63B
recommends NFKC.

A successful login checks `needs_rehash()` and re-hashes when the stored hash uses stale parameters.
Login is the one moment where both the plaintext and a database session are available, so no offline
migration script is needed. Both logins: player passwords are stored and upgraded identically.

**Player passwords are minted, not chosen, and Argon2-stored all the same.** A coach creating a
player is shown a server-generated password once (twelve characters from an alphabet with the
lookalike symbols removed, grouped for reading aloud), and only its Argon2 hash is kept; the same
one-time-reveal shape as a transfer code, but hashed as a password because a player types it at
login, where a transfer code is an unguessable 256-bit token. Regenerating it is the same mint over
again. A player row that predates sign-ins holds NULL and cannot log in until its coach mints one.

## Password validation

**The risk.** Length bounds accept `12345678`, `aaaaaaaa` and a coach's own name with a digit on the
end. Those are the first guesses any credential-stuffing run makes, so a password that meets the
bounds and nothing else is close to no password at all.

**The policy.** Every newly chosen password, at sign-up, at a reset and at a change, is checked
against the kind of list NIST SP 800-63B asks for, and refused with a 400 naming the reason. The
only bound on length is 8-128 characters, applied to `CoachCreate.password`,
`ResetPasswordRequest.new_password` and the coach and player `ChangePasswordRequest.new_password`
fields. Composition rules (a digit, a symbol, mixed case) are deliberately not part of it: the same
standard advises against them, since they push people towards predictable substitutions rather than
longer passwords.

What the list covers. The first four are arithmetic over the submitted string
(`password_policy.py`), and run first, so an obvious refusal costs no request:

- **Repetition:** one character making up more than half the password.
- **Sequences:** five or more consecutive code points, ascending or descending, so `12345678` and
  `abcdefgh` and their reverses.
- **Common choices:** a small blocklist of the obvious ones, matched against the whole password, and
  against it with trailing digits and punctuation removed so that `password!` is caught with
  `password`. A passphrase merely containing a listed word is untouched.
- **Context:** the coach's own display name or email local part appearing anywhere in it,
  case-insensitively.
- **Breached:** the password appearing in a public breach corpus, which is the "compromised" half of
  what the standard asks for and the only one of the five that leaves the process (`breach.py`).

Every rule reads the normalised form of the password, the same one that gets hashed, so an
alternative encoding of a refused string is refused too. The corpus is asked about that form
unfolded, since it is case-sensitive.

**The corpus, and what is sent to it.** Have I Been Pwned's Pwned Passwords range endpoint, which is
free, needs no key and imposes no rate limit. The password is not sent, and neither is its hash: the
password is hashed with SHA-1, the first five hex characters of that hash are sent, and the endpoint
answers with every hash in the bucket for the application to search itself. A bucket holds some 800
hashes, so the question that leaves is "is one of these 800 the coach's?", which is not a question
the answer resolves. SHA-1 is the corpus's format, not a security choice: the hash is a lookup key
for a public list. Requests ask to be padded to a uniform number of rows, so response size says
nothing about the bucket either, and the padding rows arrive with a sighting count of zero.

Two limits on that promise, both accepted. The prefix does appear in the API's own logs, since the
HTTP client logs the URL it fetched: HIBP's design already treats a prefix as safe to hand an
untrusted third party, so it is not a disclosure our own logs make worse. And only newly chosen
passwords are checked, never a login: checking at sign-in would put a network call and a prefix on
every authentication for a requirement the standard does not make.

**When the corpus cannot answer** the password is allowed through and a warning is logged. Failing
the other way would let a third party's outage close sign-up and, worse, lock a coach out of the
password recovery they are already locked out into. The four local rules still hold throughout, and
the corpus is a second layer over them rather than the only one. The checker can be switched off
entirely (`MATCHPOINT_BREACH_CHECKER=allow_all`), which is what the test suite and an offline dev
box do; production runs it because that is the default, there being no key whose absence would catch
a deployment that had quietly stopped checking.

**Where it runs.** It gates the single password write that reset and change share, and the sign-up
route calls it before the request has cost anything: before the Argon2 hash, and before the email
verification is consumed, so a refused password can be replaced rather than costing the coach a
fresh code. The reason comes back in plain language, because it is advice the coach has to act on.
The same screens run a strength meter (`@zxcvbn-ts/core`, the maintained TypeScript fork of
Dropbox's zxcvbn) in the browser, blocking submission below a score of 2; it overlaps these rules
without mirroring them, since it scores guessability rather than checking the rules above, so a
password it passes can still be refused here, and a caller that never loaded the form is held to the
rules regardless.

**Limits.** The local thresholds are loose by design: a false rejection lands on a coach mid-sign-up
with no way around it, where a miss now falls through to the corpus rather than to nothing. What
remains uncovered is a compromised password no public corpus has yet recorded, and the window in
which the corpus is unreachable and every password it would have refused is accepted.

**The minted player password deliberately skips the policy.** The rules above exist for human-chosen
weaknesses, which a uniform draw from a CSPRNG cannot exhibit except by freak accident, and that
accident would turn a player creation into a spurious 400; the breach corpus goes unasked for the
same reason, since the string has never existed before. The policy applies in full the moment a
player chooses a replacement at `POST /auth/player/change-password`, with the player's context words
being their username and full name, there being no email. Players have no reset flow at all for that
same reason: a forgotten password is a trip to the coach, whose regenerate endpoint is the recovery
path.

**MFA is deferred, not missing.** Phishing-resistant MFA (TOTP, hardware keys) is the strongest
remaining guardrail NIST's guidance recommends, but enrollment, provisioning and a login-time
challenge are more authentication hardening than this brief's club-scale coaching tool needs on top
of the live-capture workflow. The six-digit OTP above answers a different question, proving control
of a mailbox at sign-up and reset, not a factor checked at every login.

## Session management

A login mints a 256-bit random token, stores only its SHA-256 in a `coach_sessions` row, and sets
the token in an HttpOnly, SameSite=Lax cookie. Deleting the row is a complete revocation. A JWT is
stateless until revocation is needed, at which point the denylist is the sessions table by another
name, and the SPA would have to hold the token where JavaScript (and therefore XSS) can reach it.

**SHA-256, not Argon2, for the stored token.** Password hashing is expensive because passwords are
guessable; a 256-bit random token is not. The digest's only job is to make a stolen database copy
useless, and it runs on every authenticated request, where Argon2 would be a self-inflicted
performance penalty.

**`__Host-` cookie prefix.** The site is a subdomain sharing an apex. Without the prefix, a sibling
subdomain could set a Domain-scoped cookie of the same name that the browser would send alongside
the real one, enabling session fixation. The `__Host-` prefix forces Secure, `Path=/`, and no Domain
attribute, closing that vector. Conditional on the Secure flag so plain-HTTP local dev still works.

**Renewal from the halfway mark.** Sessions are long-lived (30 days) because the app must survive a
whole match offline, and an active coach who opens the app keeps their login alive indefinitely.
Only abandoned sessions reach expiry.

**Probabilistic garbage collection.** One in 50 authenticated requests sweeps all expired sessions.
Abandoned sessions (closed tabs, re-logins from other devices) are never presented again, so
per-request cleanup cannot reach them. This keeps the table bounded without a cron job.

**Player sessions are the same mechanism in a second table.** A player login mints the same kind of
token into `player_sessions`, carried in a cookie of its own name
(`__Host-matchpoint_player_session` when Secure), with the same lifetime, halfway renewal and
probabilistic sweep. A separate table and cookie rather than a principal column: the resolving
dependencies join to different tables, a revocation scoped to one player can never reach a coach's
logins by a bug in a WHERE, and a browser holding both cookies (a shared family device) has each
renewed only by its own dependency. Renewals travel to the response on one state key per principal,
so a route rotating or cancelling its own cookie cannot touch the other's.

**Regenerating a player's password revokes their sessions.** The coach's regenerate endpoint is the
recovery path and the takeover lever in one: minting over the old password ends every session it had
open, which is exactly what a coach reaches for when a credential or a device is in the wrong hands.
A player changing their own password ends every session too, the presented one included, and the
calling device continues on a fresh one, as the coach's change does. Redeeming a transfer code
deliberately revokes nothing: a transfer moves ownership between coaches, the player's own identity
and credential are unchanged, and the new coach holds the regenerate lever if they want the player
re-credentialed.

**A rotation and a sign-in cannot interleave.** A revocation deletes the session rows that exist
when it runs, so a login or a change-password that verified an unlocked read could mint one just
after the sweep and leave the revoked password holding a live, self-renewing session. All three
paths take the same row lock on `players` before they write: the two credential checks re-read the
stored hash under it and answer as a wrong password when a rotation has already landed, and the
regenerate waits for whichever request is in flight and then revokes what it minted. Without that
ordering the coach's one recovery lever could be survived by the credential it revoked, or written
over by the change-password that raced it.

**Password reset invalidates all sessions.** The purpose of a reset is that someone else may hold
the old credential; leaving their sessions alive would defeat it.

**Changing a password re-authenticates.** `POST /auth/change-password` demands the current password
rather than trusting the session: a cookie proves this browser was signed in once, not that whoever
holds it now knows the password, so without the check a stolen session is a permanent takeover. The
change then ends every session and deletes any live reset code, both being credentials the old
password left standing. The presented session is not spared: revocation matches on a token's hash,
so a thief holding a copy of that cookie sits on the same row. The device that proved the password
is handed a fresh session instead, so it stays signed in without keeping the old token.

**Closing an account re-authenticates too.** `DELETE /coaches/me` demands the current password for
the same reason, with more resting on it: the closure erases the coach and everything recorded under
them (`docs/data-model.md`), and there is nothing to recover to afterwards, so a stolen cookie alone
must not reach it. A wrong password answers 403 and is charged against a per-account budget of wrong
guesses; a correct one is never refused by that tier, so someone guessing from a session they stole
cannot lock the coach out of closing the account. The arrival tiers are charged either way, as on
every metered route here, so a flood delays a closure without preventing one. Every session goes
with the rows, and the cookie the request arrived on is cleared.

**A password write and a password check cannot interleave.** Every write commits its new hash with a
revocation of every session, so a check made against the hash it replaced must not go on to act: to
mint a session from the retired password, to write over the hash that retired it, or to erase the
account on a proof just invalidated. Each of those routes re-reads the hash under a row lock on
`coaches` before it writes, and answers as a wrong password when it has moved. Hashing stays outside
the lock, so a sign-in never holds a row waiting for Argon2.

**The closure asks for the password a screen early.** `POST /coaches/me/verify-password` checks a
password against the signed-in coach's hash and answers 204 or 403 having touched nothing, so the
form can refuse a typo where it was typed rather than at the final warning. It authorises nothing:
the closure verifies the password again on its own request, so the 204 is an answer and not a token
to spend at the next one. It also spends the closure's rate-limit tiers rather than tiers of its
own, wrong-guess budget included, so a stolen session's hunt for the password stays bounded once
across both screens instead of once per screen.

**The roster refusal is not one of these defences.** The closure also refuses while the coach still
has a player on the roster, and the request can waive that refusal. The gate exists so a player
another coach is about to take over is not erased by accident, and the password is the whole of what
stands between a stolen cookie and the erasure, waiver or not. The password is checked first for
that reason, so nothing this route answers past the 401 reaches a caller who has not just proved who
they are. A live transfer code on any player refuses closure too, and that gate has no waiver: it is
another coach's claim to redeem, not this coach's data to discard by asking to leave nothing behind
(`docs/data-model.md`).

**Deleting one player does not re-authenticate.** `DELETE /players/{id}` erases the player and their
matches on the session alone. The password guards closure because closure destroys the credential
itself, leaving nothing to refuse a later request with; a player delete leaves the account standing,
and the roster screen shows the coach what they are about to lose better than a second round trip
courtside would. A stolen cookie is bounded here by the per-coach rate limit every route charges,
and by the transfer-code refusal, which keeps a player another coach has a claim on out of reach.

## Data left on the device

Offline capture means a coach's data outlives the tab: cached reads sit in one IndexedDB database
and points not yet sent sit in another. A club device gets passed between coaches, so what happens
to those two stores when a session ends is a real decision, and it depends on how the session ended:

| How the session ended                                 | Cached reads | Outbox (unsynced points) |        Ownership record         | Last-viewed player |
| ----------------------------------------------------- | :----------: | :----------------------: | :-----------------------------: | :----------------: |
| Sign-out                                              |   Deleted    |         Deleted          |             Deleted             |      Deleted       |
| Sign-in by a different coach (or no ownership record) |   Deleted    |         Deleted          | Deleted, reset to the new coach |      Deleted       |
| Sign-in by the coach who already owns the device      |     Kept     |           Kept           |              Kept               |        Kept        |
| Session revoked server-side (401)                     |   Deleted    |           Kept           |              Kept               |        Kept        |

Sign-out and a coach switch are the same purge: signing out, or a login by a coach other than the
one the device's data belongs to, deletes the cached reads and the outbox, along with the record of
whose data it was and the marker naming the player the device last showed. The switch is detected
from the login response and completes before the first screen renders in the tab that signed in, so
nothing of the previous coach's reaches it. A purge that cannot finish refuses the sign-in rather
than going on to a device it failed to clear. The outbox rows also carry the coach they belong to,
as a backstop for a purge that never ran.

A session revoked server-side deletes only the cached reads. A 401 is not evidence that the coach
has left the device, and unsynced points are the one thing on it the server cannot send back. Cached
reads are dropped anyway, costing nothing but a refetch, and the ownership record is kept: it is
what lets the next login tell the same coach resuming from someone else arriving. A device with no
record at all is claimed by the first session the route guard confirms, so a login predating the
record is not mistaken for a stranger's.

## Cross-site request forgery

`SameSite=Lax` stops cross-site writes from carrying the cookie, but treats every host under the
same registrable domain as same-site. The app is served from a subdomain of a shared personal
domain, so a sibling host's write would arrive with the session cookie attached.

**Origin check middleware.** Every non-safe request (not GET/HEAD/OPTIONS) is refused with 403
unless its `Origin` header matches the request's `Host`. The expected origin is derived from `Host`,
not configured, so dev, tests and production need no value of their own. A missing or unparseable
`Origin` is refused. The middleware sits ahead of the session and rate-limit work, so a refused
request reads no session and spends no rate-limit token. Only the request log wraps it, so the
refusal still leaves a logged line.

## Rate limiting

Token buckets per key in process memory: per-IP, per-account and per-endpoint tiers on the endpoints
that spend real work on untrusted input, and one budget per coach across every authenticated
request.

**Token buckets over fixed windows.** What parks the threadpool is a burst, and a fixed window
admits its whole allowance in one instant (and twice that straddling a boundary). A bucket's burst
parameter is a hard cap on the instantaneous queue.

**In-process memory, not an external store.** There is one API container, so there is no second
process to share state with. A deploy emptying the buckets grants a brief grace period, not a
correctness bug. Postgres would put a write on the hot path of the flood being shed; Redis would be
new infrastructure for club-scale traffic.

**Wrong-guess budget, not arrival counting.** Login's per-account tier charges only after a failed
password verification, never on a correct password. Counting arrivals would mean anyone who knows a
coach's email (which sign-up's 409 discloses) could spend each refilling token and keep the coach
locked out indefinitely. By charging only wrong guesses, a correct password is never refused.

**Atomic multi-tier check.** When a request is counted against multiple tiers, all are checked
before any is charged. If any refuses, nothing is spent. The refusal uses the tier furthest from a
token, so the client's `Retry-After` is honest across tiers.

**Per-coach ceiling on authenticated traffic.** Every authenticated request spends from one budget
keyed on the coach, charged inside the authentication dependency itself so no new route can be added
outside it. The account is the key because behind a CDN the address is the edge's, and the charge
lands only after the session cookie proves live, so nothing an outsider sends can drain a coach's
budget. The burst is sized for the legitimate worst case, an offline outbox flushing a full match
point by point, and the sustained rate for a runaway client rather than any human.

**Recovery routes spend from a budget of their own.** A thief holding a copy of the session cookie
is the same coach to that shared budget, so ordinary-looking traffic through the stolen session
could hold it drained and leave the coach's own change-password and sign-out-everywhere answering
429: the theft turning into a denial of recovery. Those two routes therefore authenticate through a
separate dependency spending a separate per-coach budget, so however busy the rest of the API has
been made to look, the routes that end the thief's access are reachable. The reset-by-email flow is
unauthenticated and was never on the shared budget at all. The new budget is still keyed on the
coach, so a thief can drain that one too, but only by hammering the recovery routes themselves
rather than as a side effect of traffic they had reason to send. It refills at the same rate as the
budget it is carved out of, since holding a bucket empty costs its refill rate and a slower one
would leave that deliberate starvation cheaper to mount than it was before the carve-out. Keying on
the address instead would be worse, since behind the CDN it is an edge address the coach may be
arriving on as well.

**The player principal gets budgets of its own.** Player login spends login's three tiers at login's
sizes in separate buckets, so a flood at one entry point cannot price the other principal out of
signing in; the wrong-guess budget keys on the submitted username, charged only after a failed
verification, exactly as login's does on the email. Authenticated player traffic spends a per-player
ceiling charged in its own dependency, with a recovery budget carved out for the player's
change-password on the coach carve-out's reasoning. Minting a player password (creation and
regeneration, the two authenticated routes that pay an Argon2 hash per call) shares one per-coach
arrival tier, so neither route is a way around the other's bound.

**Unknown session tokens are charged after the lookup.** A cookie naming no session costs an indexed
query against the sessions table on every route that authenticates, and the per-coach budget cannot
meter it because no coach was found. A tier keyed on the caller's address is charged once the lookup
comes back empty, which is login's charge-after-failure shape for login's reason: a live session
never consults the tier, so it can never refuse a signed-in coach. Behind the CDN that address is an
edge many callers share, so the tier is sized to bound abuse by orders of magnitude rather than to
meter one caller. Draining it turns the 401 a caller with a dead cookie would have had into a 429,
which a client deciding whether its session is over has to read as an unanswered question to retry
rather than as a session still standing. Both principals' lookups charge this one tier: the cost
they meter is the same indexed miss, and a second bucket would only hand junk cookies two budgets.

## Request size limits

Request bodies are capped at 1 MB, enforced twice: by Caddy on the public path and by
`body_limit.py` inside the app (covering local dev and the direct-container path). Bodies without a
`Content-Length` are counted as they stream, so the header cannot be omitted to bypass the limit.

Without a cap, a single request could claim enough memory to crash the container (out-of-memory
kill). 1 MB is sized against the largest body the API takes, an uploaded profile photo, with room
above every other one — a full match's batch of points is a tenth of it.

Bytes are not the whole bound, because an image is not the size it decodes to: a megabyte of JPEG
allocates whatever its header claims, several bytes to the pixel. So an upload is refused on its
pixel count, read from that header before anything is decoded, and a fixed number of decodes may
hold a buffer at once — the same arithmetic against the same container memory limit as the Argon2
slots above.

## OTP codes

Six-digit numeric codes, SHA-256-stored, with a per-row attempt cap and a ten-minute expiry.

**Numeric for autofill.** Six digits earn `autocomplete="one-time-code"` autofill on iOS and
Android, directly serving the brief's low-friction sign-up goal.

**SHA-256, not Argon2.** A six-digit code is ~20 bits: GPU lanes sweep the keyspace in minutes
regardless of the hash function, so Argon2 would add hashing-slot contention for no practical
resistance. The digest keeps the plaintext out of a database copy, and the row's attempt cap is what
actually bounds guessing.

**Attempt cap in the database row, not rate-limiter memory.** Rate-limiter counters reset on deploy;
the database row's budget survives. Five wrong guesses and the row is deleted.

**`compare_digest` for verification.** The OTP row is looked up by email and the hash comparison
happens in Python. A non-constant-time comparison would leak the hash value character by character.

## Email verification

`POST /coaches` requires a valid, unexpired verification cookie matching the submitted email.
Consuming the verification token is atomic with the account INSERT (a single
`DELETE ... WHERE ... RETURNING`), so single-use needs no lock and expiry has no TOCTOU window.
Without this, anyone could create an account for any email address.

## Answered codes become a cookie

Answering a code does not spend it on the action it authorises. In both flows the row holding the
code is rewritten to hold the hash of a fresh random token instead, exactly one of the two secrets
present at any time under a database CHECK, and that token goes to the browser as a short-lived
cookie of its own name. The action then presents the cookie: `POST /coaches` for sign-up,
`POST /auth/reset-password` for a reset.

Two properties come out of it. A wrong code is refused by the endpoint whose only job is the code,
so the form can report it without a password in hand. And the credential that authorises the action
is unguessable, where the code it replaces is six digits: the code's ten-minute window and attempt
cap bound the guessing, and after that neither applies to what the caller holds.

The cookie names are distinct per flow, and each action matches the cookie against the email in its
own body, so a proof earned for one address cannot act on another.

## Player transfer codes

Moving a player to another coach is authorised by a code alone, so that the two coaches never need
accounts that know about each other. Whoever holds the code can take the player and their match
history, which makes it a bearer credential and not a reference: it is 256 random bits from the same
mint as a session token, stored only as its SHA-256, and single-use.

**Unguessable rather than short.** The prize is one player's profile and history, so the code cannot
be a six-digit number bounded by an attempt cap: there is no account to charge the attempts against,
since the code is the only thing a redemption presents. At 256 bits guessing is not a threat model,
and the authenticated per-coach rate limit is what bounds attempts.

**Redemption is atomic.** The row is selected `FOR UPDATE` and deleted in the same transaction as
the ownership change, so two coaches presenting one code cannot both win: the second waits, re-reads
its condition against the deleted row, and is refused.

**No expiry, but revocable.** The code lasts until it is used, so a player can carry it to a coach
the current one has never met. The current coach can delete an unredeemed code, which is what keeps
an indefinite capability from being permanent when it reaches the wrong person.

**Minting stops at the ownership boundary.** A code can only be minted for a player the caller
already owns, and another coach's player answers 404 like every other read of one. Ownership is
re-read under a row lock on every write to a player, so a check made before the write cannot be
stale by the time it lands: without that, the coach handing a player over could keep writing to them
after the transfer had committed.

**The player read reports that a code exists, never the code.** One screen has to survive a reload
with a transfer still pending, and two have to explain a refusal whose message names no player, so
the player read carries a boolean saying a code is outstanding, derived from the code table rather
than stored. It discloses nothing: only the SHA-256 is kept, so showing the code again is impossible
by construction, and the coach who reads the flag is the one who minted it.

**The whole profile moves, notes included.** `players.notes` is the current coach's own prose about
the player, and it travels with the row. Handing over the context a new coach would otherwise lack
is what the transfer is for, and the notes are the part written closest to that; they are the
minting coach's to edit or clear beforehand, so the mint endpoint names them among what leaves.

## Profile photos

**The filename is the credential.** A stored photo is served without a session check, under a name
of 128 random bits. The alternative costs a session lookup and a database read per image, on pages
that show a whole roster of them, to guard a cropped photograph rather than account data. What it
does not do is expire: anyone handed a URL keeps it. Replacing or clearing a photo stores the new
one under a new name and deletes the old file after the row committing to the new one, so a URL that
has been handed out dies with the photo it named rather than outliving it, except in the crash
window between that commit and the unlink, the one case nothing here reclaims
(`docs/data-model.md`). Serving checks only that the file exists, not that a row still names it, so
a crash in that window leaves the old URL answering with a photo no row points to for as long as the
file sits unremoved.

**Re-encoding is the sanitiser.** Nothing that arrives is stored. Every upload is decoded and
written out again at one fixed size, so the bytes served share nothing with the bytes submitted and
no malformed or polyglot container survives to be handed back from our own origin. That is also what
removes the camera metadata a phone attaches, including the coordinates a photo was taken at, which
matters here because the subjects are players and some of them are children. The formats a decoder
will be pointed at are an allowlist checked from the header first, which is what keeps the plugins
that shell out to an external interpreter out of reach.

**The name reaches the logs.** A request for a photo is logged like any other, path included, so the
credential appears in the container logs and in Caddy's. Accepted rather than redacted: the log sits
on the same disk as the file it names, and anyone who can read one can read the other.

## Secret redaction in validation errors

FastAPI's default 422 handler echoes the submitted body in `detail[].input`. A rejected sign-up
would reflect the coach's chosen password into browser devtools, proxy logs, and error-reporting
services. A global exception handler recursively redacts `password`, `otp`, and `new_password`
fields from the echoed input. A test fails if any schema adds a `SecretStr` field not listed in the
redaction set.

`SecretStr` alone is insufficient: it handles reprs and tracebacks, not FastAPI's error body.

## Secret redaction in logs

The same posture over the request log (`logs.py`). The line each request emits carries method, path,
status, duration and ids, never a body, header or query value, so a credential has no path into it
by construction. A processor redacts any field whose key contains a secret stem, at any depth, as
the backstop for log calls that design cannot see, and a test drives the sign-up, login, OTP and
password-reset flows asserting no credential value reaches stderr.

The one field that can hold arbitrary text is a rendered traceback. `hide_parameters=True` on the
engine (`db.py`) keeps bound SQL parameters out of the DBAPI error messages that end up in one.

## Unhandled exceptions

The traceback above is for us, and a failure the code did not anticipate is the one place its
internals could reach a client instead: an exception message names tables, files and providers, and
Starlette's default 500 would carry whatever it says. A handler on `Exception` (`errors.py`) answers
every one of them with the same static sentence, and attaches the request id that identifies the
logged traceback, so a report is traceable by an id that discloses nothing.

An exception this handler catches has already unwound past every ASGI middleware, including the one
that stamps the security headers below, so it stamps that same header set itself rather than letting
a crash answer with none of them. A crash is not a special case the headers skip.

Declared error responses are unaffected: they are resolved before an exception reaches this handler.
The one way past it is Starlette's debug mode, which is checked first and renders the traceback as a
page, so `MATCHPOINT_DEBUG` belongs to development and stays unset wherever the app is deployed.

## Authorisation boundaries

**404, not 403, for another coach's resources.** A request for a player or match belonging to
another coach returns 404. A 403 would confirm the row exists, which is the same enumeration concern
as the authentication design above.

**Photos are the documented exception.** A stored photo is reachable by URL without a session, so it
is not scoped to a coach the way every other resource is. The photo section above records what that
means and why it is the trade worth making.

**No coach list endpoint.** No route returns a coach other than the caller's own. A list route would
be an open dump of every coach's email address. Pinned by a test asserting `GET /coaches`
returns 404.

**A player session reaches exactly its own player.** The player principal is lower-privilege by
construction: it authenticates a player's own login, logout, change-password and
`GET /auth/player/me`, and no route it reaches answers with a row belonging to anyone else. The
self-view is trimmed to match, carrying none of the coach-facing fields: the coach's notes about the
player stay the coach's, and the ownership and transfer plumbing stays coach workflow. Any route
opened to this principal is held to the same two rules, the player's own rows and none of the
coach's columns. A coach session is nobody to a player route and a player session nobody to a coach
route, which the two distinct cookies enforce. Regenerating a player's password sits on the coach
side of the line and answers the same 404 for another coach's player that every player route does.

**Accepted residual channel: a minted username counts namesakes deployment-wide.** Usernames are
unique across every coach, because the sign-in form has nothing but the username to look a player up
by, so the number a new player is given tells the coach who created them how many players of that
name already exist under other coaches. The count is the whole of it: no name, no id, no coach, and
no way to ask again without creating another player. Numbering per coach instead would mean the
login lookup needing a coach it has not got.

## Server-side request forgery

**No caller-named host is ever reached.** The API's only outbound connections are to Resend (URL
fixed as a module constant in `mail.py`, pinned by a test), Have I Been Pwned (the same, in
`breach.py`) and Postgres (DSN from the environment). None takes a hostname from a request, and the
one path segment any of them builds from submitted data is five hex characters of a SHA-1 hexdigest,
so it is `[0-9A-F]{5}` by construction and cannot traverse or redirect anywhere. Caddy's upstream is
likewise fixed in the Caddyfile. `EmailStr` validates syntax only (`check_deliverability=False`),
and OTP emails carry a code, not a link, so no submitted value becomes a network destination.

**Starlette's trailing-slash redirect is proxy-contained.** `redirect_slashes` builds its 307
`Location` from the `Host` header, but Caddy's site block matches one hostname, so a forged `Host`
never reaches the API. Documented rather than disabled because turning it off would 404 every
trailing-slash request.

**httpx does not follow redirects by default.** `mail.py` and `breach.py` inherit this default, so a
third party answering 3xx fails the call rather than hopping to a new destination.

## Infrastructure

**Single-origin architecture.** Caddy serves the SPA and reverse-proxies `/api/*` from one origin.
Same-origin means no CORS configuration, no `SameSite=None` cookies, and the HttpOnly, SameSite=Lax
session cookie works without cross-origin headers.

**Firewall.** UFW on the VPS allows inbound 80/443 only from Cloudflare's published IP ranges.
Without this, Cloudflare's origin-IP-hiding is undermined by direct connections.

**Container hardening.** The API container runs as an unprivileged user with a root-owned `/app`.
All containers get `cap_drop: [ALL]` (Caddy gets `cap_add: [NET_BIND_SERVICE]`) and
`no-new-privileges`. A full non-root Caddy was rejected because the origin private key must be
readable regardless, and remapping port 80 couples three files for no gain at this threat level.

**Deploy secrets.** Neither `POSTGRES_PASSWORD` nor any signing key is stored in CI variables. The
database password lives only on the VPS, since CI builds images and hands the VPS a tag but never
talks to Postgres. `deploy.sh` writes `.env` to a temp file with mode 0600 before an atomic rename.

## Security headers

**Split.** Caddy sets the app shell's headers (`infra/prod/Caddyfile`); API responses carry their
own from middleware (`headers.py`). A header set only at the proxy is absent whenever the proxy is
not in front of the API, and the middleware's set is assertable in tests.

**Content-Security-Policy.** The shell's policy is same-origin (`default-src 'self'`), which holds
because the built app loads nothing external: no CDN scripts, no fonts, no analytics, and no inline
script tags. The one carve-out is `style-src 'unsafe-inline'`: Base UI's overlay components inject
scroll-lock `<style>` elements at runtime, and a nonce cannot authorise them because the app shell
is a static file the service worker precaches, so a per-response nonce would go stale in the cache.
Inline styles alone are a small concession; script execution, where XSS lives, stays same-origin.
API responses get `default-src 'none'`, since JSON should never execute, render, or be framed. The
exception is Swagger UI, kept available in production and served a relaxed policy of its own
admitting its CDN assets and inline bootstrap; the relaxation is scoped to that one HTML page, so no
data response ever inherits it. ReDoc is disabled rather than granted a second, larger exemption.

**HSTS.** `max-age=31536000; includeSubDomains`, set at the origin and passed through by Cloudflare.
A year immediately, not a ramp: the domain sits behind Cloudflare with TLS permanently on, so there
is no plain-HTTP future to be locked out of. No preload, which commits the registrable domain, and
the app lives on a subdomain of one the project does not control.

**The rest.** `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer` everywhere (a
private coaching tool has no reason to advertise its URLs off-site), and framing forbidden via both
`frame-ancestors 'none'` and the legacy `X-Frame-Options: DENY`. No `Permissions-Policy` is set: the
defaults already gate powerful APIs to same-origin, and the capture screen's Screen Wake Lock must
stay available.

## Supply chain

pnpm's `minimumReleaseAge` rejects packages published in the last day, blunting the window for
compromised-release attacks. pnpm also skips install scripts for non-approved dependencies by
default.
